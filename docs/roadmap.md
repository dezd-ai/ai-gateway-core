# 增长路线（Roadmap）

> 本文件规划「让项目被更多人用起来」的**功能路线**，与 [backlog.md](./backlog.md)（缺陷/安全待办）区分：
> - backlog = 修错、补安全（先做，影响可信度）；
> - roadmap = 增长功能（让人记住、让人迁移）。
> 状态随实现推进更新。

---

## 0. 战略定位（楔子）

**一句话定位**：零依赖 · 单二进制 · 毫秒级启动的 AI 网关——国产模型开箱即用，流式审计帮你省钱。

**竞争参照**（2025 现状）：
- [LiteLLM](https://github.com/BerriAI/litellm)：Python，虚拟 key / 预算 / fallback / 100+ 供应商，生态最大；
- [new-api](https://github.com/sanjiuershiqi/new-api)（One API 二次开发）：国内事实标准，token 计费 + 用户系统 + 支付 + Midjourney/Suno 代理。

**结论**：不与两者拼功能广度（必输），把「零依赖 + 边缘/内网 + 国产计费精度」凿深；增长功能围绕该楔子排序。

### 0.1 Agent/Harness 时代的定位（2025-08 决策）

> 背景：agent/harness 成为主流 AI 消费方，且持续进化（长推理、工具调用、自适应重试）。

**核心原则：网关是「AI 流量的治理层」，不是「干预层」。**

| 原则 | 含义 |
|---|---|
| **对 agent 隐形** | 不悄悄换模型、不注入内容、超时/body/限流可按 agent 场景放大、SSE 严格兼容——**谁在 agent 链路上添乱，谁就被绕过** |
| **对平台显形** | 审计全量、成本治理（谁/哪个 agent/哪个任务花了多少）、安全合规（PII/敏感数据不出域）、供应商治理（统一密钥/切换策略）、可观测（全链路 trace/成本报表） |
| **不干预任务** | agent 优化「单次任务」，网关治理「全局系统」——只管策略/审计/成本/安全，把「智能」完全让给 agent |

**对现有功能的影响**：
- 内容路由/时间路由/fallback 降级 = **受控流量的省钱工具，绝不默认对 agent 生效**（按 key/路径隔离，agent 流量宽松模式只开审计+限流）；
- 增长点：**MCP 兼容**（agent 标准协议）、agent 专用宽松模式、多租户计费、agent 安全边界（prompt 注入检测/工具调用审计）。

**取舍标尺**：后续任何功能，先问「这是治理（做）还是干预（不做）」。

| # | 功能 | 现状 | 价值 |
|---|---|---|---|
| R1 | vKey 生命周期（keygen / 过期 / 吊销）+ 限流 + 配额/日预算 | ❌ vKey 明文无管理（README 已知限制 7）；**设计要点见 [backlog.md](./backlog.md) 1.6**（keygen 可查可作废 + 审计兜底、限流额度跨 reload/重启保留、多实例近似） | new-api 火的核心；补最大短板 |
| R2 | **请求级失败 fallback/重试**：选中节点失败 → 自动切另一上游（或降级模型档位） | ⚠️ 仅有断路器级切换（**本次请求失败不重试**，直接 502/503）；**设计已定稿 → [fallback-design.md](./fallback-design.md)，当前优先实现** | LiteLLM 核心卖点；消除"一次 502 毁一个请求" |
| R3 | 模型别名映射 + `/v1/models` 动态端点 + OpenAI SDK 开箱兼容 | ✅ **已实现**（[model-alias.md](./model-alias.md)）：injector 内别名翻译（白名单校验真实名）+ GET `/v1/models` 按 vKey 白名单过滤 | 用户零改代码迁移（openai-python 直连）；开源入场券 |
| R4 | 协议广度：智谱 / 豆包 / 月之暗面 / 讯飞 + 本地 Ollama / vLLM | ⚠️ 仅 openai + baidu_wenxin | 国内"全家桶"预期（new-api 靠此赢） |
| R5 | 多租户用量/成本/配额看板（obs 从只读升级为运营面板） | ⚠️ obs 只读日志，无配额/告警 | 从"工具"变"产品"的分水岭 |
| R6 | 语义缓存（请求级缓存命中）+ 缓存命中报告 | ❌ | "省钱"是最易传播的卖点；结合已有官方计费精度 = 成本报告故事 |

## 4. 首发推荐（按投入产出比）

1. **R1 vKey 生命周期 + 限流配额** —— 补最大短板，需求已被 new-api 验证；
2. **R2 请求级 fallback（当前优先，设计已定稿 [fallback-design.md](./fallback-design.md)）+ R3 模型别名** —— 让「多模型接入」真正可用；
3. **R7 一键体检报告** —— 把已有能力变成传播素材。

做完这三点，项目从「原型」变「可用的工具」，再谈开源运营。

> 执行顺序约定：**backlog 阶段 1（缺陷修复）→ R2 fallback（M1→M3）→ R1/R3 → R7**；R17 内容路由在 R2 落地后进入实施。

## 5. 现实检查

- 功能是**必要不充分**：火不火 = 楔子 × 痛点 × 运营 × 运气；
- **先做「可信」再做「记住」**：基础设施（R1-R6）未补齐前，花哨功能放大不信任；
- **二选一或分阶段**：通用云网关赛道（对标 LiteLLM）与边缘差异化赛道（战略文档方向）是两条路，建议先凿后者——那才是别人抄不走的位置；
- 本 roadmap 与 backlog 的执行顺序：**backlog 阶段 1（缺陷修复）→ 本文件第一梯队 → 第二梯队**。
